🐾Artifact to App

From an AI-generated HTML mockup to a verified full-stack application — in seven prompts, with a human at every gate.

The 20-minute tour of the two-hour Artifact to App workshop. Nothing to type today — just the shape of the thing and what each step produced.

Welcome. Recently a group of us spent two hours turning a pretend app into a real one, using Claude. This is the 20-minute version for everyone who couldn't be there. You don't need to type anything. I want you to leave with three things: the shape of the process, why the human gates are the point, and what actually came out of each prompt — with real-looking excerpts so it isn't hand-waving. Ground rule for me: 20 minutes is tight. Every slide has a time chip in the corner; if I'm over, I skip the 'on-ramps' slide and squeeze the capstone.
The problem

A beautiful, hardcoded lie

The starter is Pet Care Coach: pets, symptom reports, vet appointments. It looks finished. You can add Maple's "low energy, skipped breakfast" report. It shows up. It works.

Then you refresh the page.

Everything is gone. The data was a JavaScript variable. There is no database, no API, nothing behind the curtain.

Sample data lives in the component. Refresh = amnesia.

This is the motivating demo. In the workshop I click around live: log a report for Maple, then hit refresh, and it vanishes. The line I use: "Everything you just saw was a lie — beautiful, hardcoded lies. Today we make it true." The point of the code on the right isn't the code. It's that the data is nested inside the UI: reports and appointments live inside each pet. That nesting is exactly what a database has to untangle, and it's what Claude has to notice in Prompt 1. Notice too there's nothing in that file hinting at a schema. That's deliberate — the starter is "innocent" so the analysis happens honestly.

✋ = a gate. Nothing continues until a human decides. Three of them, and they're the whole point.

Claude infers a data model from the UI, asks about what the UI leaves ambiguous, a human confirms a spec, and only then does code get generated — twice: once as an in-chat artifact, once as a real project.

The thing being taught is not any single prompt. It's the rhythm. AI does the typing; you do the deciding.
This is the whole workshop on one slide; everything after this is zooming in. Walk left to right. Prompt 0 is optional on-ramps. Prompt 1 is analysis only — Claude is forbidden from writing code. Gate one: it asks questions, humans answer. Prompt 2 turns those answers into SPEC.md, a document that every later prompt cites. Gate two: a human approves the spec, out loud, in the chat. Then two builds from the same spec: an artifact that runs inside the Claude chat window, and a real Next.js project. Gate three: code review of one route and one component. Prompt 6 proves it works and packages it. The amber gates are the point. The prompts are copy-paste; the decisions at the gates were the actual work in the room.

Prompt 0A · 0B

Where the mockup comes from

optional on-ramps

0A — idea → prototype. Two passes, on purpose. Pass 1 is a few plain sentences:

I have an idea for a small web app called Pet Care Coach. It's a simple health-record tracker for pet owners… Build me a quick clickable prototype as a single, self-contained HTML file (inline CSS and JS, no build step, no backend)… It's fine if everything resets on refresh — I just want to see the idea.

Pass 2 levels up the brief: two screens, teal accent, three named sample pets, the empty state for Biscuit the rabbit. The result: a clickable prototype like today's starter.

0B — plain HTML → React. Only if what you have is old-school HTML:

Convert it to a single-file React component… Preserve all hardcoded sample data exactly as it is. Local component state only — do not add persistence, a data layer, routing libraries, or any new features. This is a straight translation.
What it produced: a same-looking, same-behaving React file — and a short list of anything that didn't translate one-to-one.
Quick one, and the first to cut if I'm behind. Prompt 0A is where the mockup itself came from: a rough prompt to see the idea, then a refined brief once there's something to react to. The teaching point is that the rough pass exposes every decision Claude made on your behalf — what fields a pet has, what "urgency" looks like — so you can keep or override them. That back-and-forth is the skill, not the prompt. 0B is the on-ramp for legacy HTML: convert it to React, change nothing else. Then everyone in the room switches to the shared starter so we're all staring at the same ambiguities.
Prompt 1

Analyze the UI — and ask, don't build

gate: humans answer
I want to turn this frontend into a database-backed web application… This first step is analysis only — do not write any application code yet. 1. Identify every kind of data the UI displays or collects, including data that is nested inside other data. 2. Propose a relational data model… 3. List every assumption you had to make. 4. Ask me numbered clarifying questions wherever the UI is genuinely ambiguous about the data. Pay particular attention to: values that might be fixed lists vs. free text; displayed values that might be stored vs. derived; text that might really be a date, time, or number… Wait for my answers before proposing the final schema.

What came back — a model and a list of questions, no code:

Proposed tables
  pets · symptom_reports · appointments
  (reports and appointments are nested in
   the UI → they become child tables with
   a pet_id foreign key)

Questions before I finalize the schema
1. Pet age is shown as "6y". Store the
   age, or a birthdate and compute it?
2. Appointment status shows Upcoming /
   Completed. Stored, or derived from
   the appointment time?
3. "2026-09-14 · 10:30 AM" is a display
   string. Store as text or a timestamp?
   … (seven questions in all)
This is the prompt that makes the workshop work. Note the two highlighted constraints: no code, and wait for my answers. Claude reads the mockup and comes back with a proposed model — three tables, because it noticed the nesting — and a numbered list of questions. In the workshop this is a game: the starter has seven ambiguities planted in it, and the room gets to argue about each one before we settle on an answer. I'm going to show you three of the seven on the next slide and keep the other four for the next time we run it. If your Claude jumped ahead and wrote code, you get to scold it: "Stop — ask your clarifying questions first." That works almost every time, and it teaches that the gates are instructions you're allowed to enforce.
Gate 1 · the question game

The UI lies by omission — three of the seven

Age is displayed as "6y". Store the age? Tempting: yes, it's right there on the card. Store birthdate; compute the age. Stored age goes stale. Maple has a birthday. Someone in the room always spots it — applause moment.
Status shows Upcoming / Completed. Stored, or derived from the date? Tempting: "just compare to today." Stored column, CHECK (Upcoming, Completed, Cancelled). "What about Cancelled?" You can't derive that from a timestamp. The room discovers it themselves.
"2026-09-14 · 10:30 AM" — store that string? Tempting: it's what the screen shows. A real scheduled_at timestamp; formatting is the UI's job. Never store display strings. You can't sort, filter, or reschedule a sentence.

The other four ambiguities are deliberately not on this slide — they're yours to argue over at the next full workshop.

Three examples of what a mockup can't tell you. Age: the card says 6y, but stored age rots — store the birthdate. Status: everyone's first instinct is derive it from the date, and then someone says "what about Cancelled?" and the whole room sees why it has to be a stored column with a fixed set of values. Timestamp: never store the display string. The meta-point: these aren't database trivia. They're decisions a human had to make, and Claude had to ask about, before a single line of code existed. This is where AI fluency shows up — knowing to demand the questions instead of accepting the first confident answer. Deliberately not spoiling the other four.
Prompt 2

The spec is the contract

gate: "SPEC approved, continue"

Answers go in first, then the prompt: "write a SPEC.md that will be the single source of truth for everything we generate next… Do not generate any application code until I approve the spec."

## 1. Data model
### pets
| column    | type       | notes                    |
| id        | integer PK | auto-increment           |
| name      | text       | required                 |
| species   | text       | Dog/Cat/Rabbit/Other     |
| breed     | text       |                          |
| birthdate | date       | age computed for display |
| created_at, updated_at | on every table          |

### appointments
| pet_id            | FK → pets                    |
| symptom_report_id | FK → symptom_reports, NULL ok|
| visit_type        | text                         |
| scheduled_at      | timestamp — UI formats it    |
| vet_name          | text                         |
| status            | text CHECK (Upcoming,        |
|                   |   Completed, Cancelled)      |
## 2. REST API
GET/POST        /api/pets
GET/PUT/DELETE  /api/pets/:id
GET/POST        /api/symptom-reports?petId=
GET/POST        /api/appointments?petId=
… list · get-one · create · update · delete, every entity

## 3. Data interface   ← the UI only calls these
listPets · getPet · createPet · updatePet · deletePet
listSymptomReports(petId) · createSymptomReport · …
listAppointments(petId) · createAppointment · …
Every function maps to exactly one endpoint.

## 4. Seed data
Maple   (Dog, Lab mix, born 2020-05-11) · 2 reports · 2 appts
Juniper (Cat, shorthair, born 2023-06-30) · 1 · 1
Biscuit (Rabbit, Holland Lop, born 2024-04-02) · none

## 5. Locked v1 constraints
SQLite via Drizzle, clean path to Postgres · integer PKs
created_at/updated_at everywhere · no triggers or views
no auth in v1 — but designed so adding it is a clean step
Prompt 2 turns the room's answers into SPEC.md. Five sections: the confirmed data model — notice birthdate, notice the nullable symptom_report_id, notice status as a stored CHECK column; those are the answers from the question game, written down. Then the API surface, the data interface — the short list of function names the UI is allowed to call — the seed data, and the locked constraints. Then the second gate, and I make it visible: someone types "SPEC approved, continue" into the chat. Nothing gets built that isn't written down and approved. If you've heard of spec-driven development tooling like OpenSpec, this is that ritual, done by hand so you feel it.
Prompt 3

App #1 — the artifact that remembers

the gratification spike

"Build a version I can use right now… all data access goes through the data interface in SPEC.md, implemented with a storage adapter backed by window.storage, so my records survive closing and reopening this conversation."

// the storage adapter — the artifact's "database"
const KEY = "petcoach:v1";
async function load() {
  try { const r = await window.storage.get(KEY);
        return r ? JSON.parse(r.value) : null; }
  catch { return null; }
}
async function save(s) { await window.storage.set(KEY, JSON.stringify(s)); }

export const db = {
  listPets:  async () => (await state()).pets,
  getPet:    async (id) => (await state()).pets.find(p => p.id === id),
  createPet: async (input) => {
    const s = await state();            // stored blob, or the SPEC seed
    const pet = { id: nextId(s.pets), ...input, createdAt: now() };
    s.pets.push(pet); await save(s); return pet;
  },
  createSymptomReport: async (input) => { /* same shape */ },
  createAppointment:   async (input) => { /* same shape */ },
  resetDemoData:       async () => save(seedFromSpec()),
};

// …and in the component, the button has no idea any of this exists:
<button onClick={() => db.createPet(form).then(refresh)}>Add pet</button>

What it produced: a working Pet Care Coach inside the chat.

  • Add a pet, log a report, schedule an appointment.
  • Close the conversation. Reopen it. Still there.
  • Open the same chat on your phone — there's your app.
  • A "Reset demo data" button restores the seed.
The components call db.createPet, not storage. The UI has no idea where the data lives. Hold that thought.
This is the moment the room lights up. Fifteen minutes after the spec was approved, everyone has a working app running inside their Claude chat, and it remembers. Claude artifacts have a small persistent pocket — window.storage — and we use it as a stand-in database. Step through the code highlights: the adapter loads and saves a blob; the db object exposes exactly the names from SPEC.md; and the button in the component calls db.createPet and nothing else. That last line is the setup for the punchline in Prompt 5. In the workshop this is five minutes of free play — add your own actual pet — then the kicker: close the chat, reopen it, data's still there.
Prompt 4

App #2 — the real database layer

gate: schema files match SPEC

"Now we build the real application from the same SPEC.md… in stages so I can review each layer." → a Next.js project: db/schema.ts, schema.sql, a re-runnable db/seed.ts, lib/data.ts (the only file that touches the DB), and middleware.ts — empty except for one comment: "future authentication insertion point."

db/schema.ts — the ORM rendering

export const pets = sqliteTable("pets", {
  id:        integer("id").primaryKey({ autoIncrement: true }),
  name:      text("name").notNull(),
  species:   text("species").notNull(),
  breed:     text("breed"),
  birthdate: text("birthdate").notNull(),   // ISO date
  createdAt: text("created_at").notNull().default(now),
  updatedAt: text("updated_at").notNull().default(now),
});

export const appointments = sqliteTable("appointments", {
  id:              integer("id").primaryKey({ autoIncrement: true }),
  petId:           integer("pet_id").notNull()
                     .references(() => pets.id),
  symptomReportId: integer("symptom_report_id")       // nullable
                     .references(() => symptomReports.id),
  visitType:       text("visit_type").notNull(),
  scheduledAt:     text("scheduled_at").notNull(),     // ISO timestamp
  vetName:         text("vet_name").notNull(),
  status:          text("status", { enum: STATUSES }).notNull(),
  /* createdAt / updatedAt as above */
});

schema.sql — the same model, as plain SQL for humans

CREATE TABLE pets (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  name       TEXT NOT NULL,
  species    TEXT NOT NULL,
  breed      TEXT,
  birthdate  TEXT NOT NULL,  -- age computed, never stored
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE appointments (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  pet_id            INTEGER NOT NULL
                      REFERENCES pets(id),
  symptom_report_id INTEGER              -- optional link
                      REFERENCES symptom_reports(id),
  visit_type        TEXT NOT NULL,
  scheduled_at      TEXT NOT NULL,       -- ISO timestamp
  vet_name          TEXT NOT NULL,
  status            TEXT NOT NULL CHECK (status IN
                      ('Upcoming','Completed','Cancelled')),
  /* created_at / updated_at as above */
);
Same spec, second build — and we build it in layers so each one can be reviewed. This stage is skeleton plus database only. The review moment is putting SPEC.md, schema.ts and schema.sql side by side: one model, three renderings. Birthdate, nullable report link, status CHECK — every decision from the question game is here, verbatim. For the technical folks this is the Drizzle pitch. For everyone else the sentence is: the spec became real. And point at middleware.ts: an empty file with a single comment. That's where sign-in goes in the sequel workshop. We planned the extension before writing v1 — that's the whole trick to not painting yourself into a corner. Prep note that bit us: Prompt 4 now insists on pinned versions, because a bare TypeScript install pulls TS 7 and Next.js 15 refuses to build against it.
Prompt 5

The API — and the adapter payoff

gate: review one route + one component

app/api/pets/[id]/route.ts — a thin wrapper over lib/data.ts, no database code in routes

import { getPet, updatePet, deletePet } from "@/lib/data";

export async function GET(_req: Request, { params }: Ctx) {
  const pet = await getPet(Number(params.id));
  return pet
    ? Response.json(pet)
    : Response.json({ error: "Not found" }, { status: 404 });
}

export async function PUT(req: Request, { params }: Ctx) {
  const body = await req.json();
  if (!body.name)
    return Response.json({ error: "name is required" }, { status: 400 });
  const pet = await updatePet(Number(params.id), body);
  return pet
    ? Response.json(pet)
    : Response.json({ error: "Not found" }, { status: 404 });
}

"Summarize what changed in the components" → almost nothing. Loading and error states added; hardcoded data removed; every call still goes to db.*.

lib/client-db.ts (real app) next to the artifact's storage adapter — same names, same shapes, different backend

// fetch adapter — real app
export const db = {
  listPets:  () => api("GET",  "/api/pets"),
  getPet:    (id) => api("GET", `/api/pets/${id}`),
  createPet: (input) => api("POST", "/api/pets", input),
  createSymptomReport: (i) => api("POST", "/api/symptom-reports", i),
  createAppointment:   (i) => api("POST", "/api/appointments", i),
};
// storage adapter — artifact (Prompt 3)
export const db = {
  listPets:  async () => (await state()).pets,
  getPet:    async (id) => (await state()).pets.find(…),
  createPet: async (input) => { /* push + save */ },
  createSymptomReport: async (i) => { /* … */ },
  createAppointment:   async (i) => { /* … */ },
};
Same components. Same interface. Two adapters. That's why one app ran in two worlds.
Prompt 5 generates the REST routes from the spec — thin wrappers, real status codes, 404 and 400 where they belong — and ports the UI into the project with a fetch-based adapter instead of the storage one. The teaching moment is the diff. I ask Claude to summarize what changed in the components and the honest answer is "almost nothing". Then the right-hand column: client-db.ts on top, the artifact's storage adapter below. Same function names. Same shapes. One talks HTTP, one talks to Claude's storage pocket. Point back at the whiteboard diagram from slide four — this is the lecture's thesis proven in code. It's also the same trick that later lets you swap SQLite for Postgres, or add sign-in, without touching the UI.

Claude installs, pushes the schema, seeds, starts the server, and then hits it with real HTTP requests — list, get, create, update, delete for every entity, one realistic end-to-end flow, and a restart to prove the data lives on disk. Capstone

Make the prompts disappear

You ran seven prompts and made maybe ten decisions. The prompts are now overhead — the decisions were the work. So the whole pipeline gets packaged as a Claude skill: instructions Claude follows on its own, gates included.

---
name: ui-to-database-app
description: Turn a frontend-only UI (React or plain HTML) into a
  database-backed web application through a gated, spec-driven
  pipeline. Use whenever the user provides a frontend and asks to
  make it a real app, add a database, or make its data persist…
---
# UI → Database-Backed App
You are running a staged pipeline… The pipeline has **human
approval gates** — never skip ahead of a gate, even if you are
confident. The user decides; you generate.

## Pipeline
### Step 1 — Analyze and ask (NO CODE)
### Step 2 — Spec (wait for approval)
### Step 3 — Artifact app · Step 4 — DB layer · Step 5 — API + UI
### Step 6 — Verify and package

The mic-drop demo, in a fresh chat: attach the plain-HTML starter and say only

Turn this into a database-backed web app.

Claude walks the whole pipeline — asks the clarifying questions, pauses at the spec gate, builds both apps, verifies.

Lives at skill/ui-to-database-app/SKILL.md. Domain-agnostic: point it at any frontend.

The capstone reframes the whole session. The prompts you just watched were scaffolding. Once you know the decisions, the prompts are overhead — so we package the pipeline as a skill. The frontmatter tells Claude when to use it; the body is the pipeline as instructions, with the gates written in: never skip ahead, the user decides, you generate. Then the demo: fresh chat, attach the HTML mockup, one sentence. Claude asks the questions, stops at the spec gate, and waits for a human. The gates survived being automated. That's the AI-fluency lesson in one line: encode your judgment as the process, not as a prompt you have to remember.
